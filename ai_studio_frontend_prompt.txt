----------------------------------------------------------------
PROMPT STARTS HERE
----------------------------------------------------------------

Build a React + TypeScript + Vite single-page web app called
"JARVIS Organism Console" -- a live operator console for a personal
AI-assistant backend called JARVIS. It is a dark-themed, dense,
professional systems-monitoring dashboard (think: a mix of a
terminal, Grafana, and a chat app), NOT a consumer chat-bot UI.

--------------------------------
1. AUTH / LOGIN
--------------------------------
- A simple login screen gates the whole app. Single user, no signup
  flow needed: a username + password form (or password-only is fine)
  that POSTs to an auth endpoint and stores a token/session.
- Until integrated with the real backend, mock this: any non-empty
  password succeeds and stores a fake token in memory (not
  localStorage -- keep everything in React state/context so it's easy
  to swap for a real call later).
- After login, land on the Dashboard (section 3).
- Include a visible "Log out" control.

--------------------------------
2. OVERALL LAYOUT
--------------------------------
- Persistent left sidebar (or top tab bar on narrow screens) with
  three sections:
    a) DASHBOARD -- the live organism monitor (section 3)
    b) VIRTUAL CLI -- a terminal-style chat replica (section 4)
    c) TRACE INSPECTOR -- full per-turn deep trace viewer (section 5)
- Dark theme: near-black background, cyan/green accent for "healthy/
  online" states, amber for warnings, red for errors, muted gray for
  idle/dim text -- matches a terminal aesthetic, monospace font for
  all data values and the CLI panel (a regular sans-serif is fine for
  labels/headers).
- Everything on the Dashboard auto-refreshes by polling every 1-2
  seconds (configurable). Build a small typed API client module
  (e.g. `src/api/client.ts`) that every screen calls through -- do
  NOT scatter fetch() calls across components -- so swapping mock
  data for the real backend later is a one-file change.

--------------------------------
3. DASHBOARD SCREEN
--------------------------------
This mirrors a terminal tool called `monitor.py` that already exists
for this backend. Recreate its content as a proper web dashboard with
cards/panels instead of monospace text blocks:

  a) STATUS HEADER
     - Big, unmissable "● WORKING" (green, pulsing) or "○ IDLE" (gray)
       indicator.
     - Current pipeline stage as a horizontal step indicator:
       IDLE -> PERCEIVING -> INDEXING -> EXECUTING (highlight the
       active one).
     - A warning banner that appears only when `fallback_active` is
       true: "Last extraction used the deterministic safe fallback".
     - pid, runtime status (ONLINE/OFFLINE), last-updated timestamp
       ("3s ago" style, recomputed client-side every second).

  b) SYSTEM RESOURCES card
     - RAM (max RSS, in MB), CPU user/system seconds, thread count.
     - LLM backend name, ready boolean, whether the local model is
       loaded, and a small "budget" gauge: calls used / max calls
       this turn, tokens reserved / max tokens this turn.

  c) RECENT ACTIVITY HISTORY card
     - A vertical timeline / table: each row is one completed "turn"
       -- start time, end time, duration, and the stage path it took
       (e.g. "PERCEIVING > INDEXING > EXECUTING > IDLE"). Show the
       last 10. An in-progress turn (no end time yet) shows as an
       active/pulsing row instead of a finished one.

  d) RECENT SCHEMA EXTRACTIONS card
     - A list: schema name, which stage resolved it (primary /
       refined / safe_fallback -- color-code: green / amber / red),
       and the per-attempt sequence (e.g. "primary:fail -> refined:ok").

  e) BACKGROUND LEARNING QUEUE card
     - worker alive (bool), currently running a job right now (bool,
       show as an animated dot), pending / processed / failed /
       dropped counters.

  f) LEARNING & EVOLUTION card -- "what has JARVIS actually learned"
     - Self-evaluation: turns evaluated, success rate (%), average
       score, last-evaluated time.
     - Knowledge: built / accepted / rejected / pending-review counts.
     - Evolution: proposals / approved / applied counts. If proposals
       exist but none are applied, show a small note explaining that
       evolution requires explicit approval (nothing auto-applies).

  g) ORGANISM HEALTH card
     - Heartbeat alive + beat count, organs online/total (as a small
       grid of organ-name chips, green if attached).

  h) RECENT INTERNAL LOG card
     - Last 5-8 warning/error log lines with timestamp, level badge,
       tag, message. This is internal diagnostic noise that used to
       print into a terminal -- style it like a compact log viewer.

--------------------------------
4. VIRTUAL CLI SCREEN
--------------------------------
A terminal-style replica of the backend's own CLI chat tool:
  - A scrolling message history (user messages right-aligned or
    marked, JARVIS replies left-aligned/marked) with monospace font
    and a blinking cursor input line at the bottom, styled like a
    real terminal prompt (e.g. "UK > ").
  - After every JARVIS reply, render a compact "workflow panel"
    directly under that reply showing 5 stage rows, exactly like the
    Dashboard's pipeline stages but scoped to that one turn:
        1. PERCEPTION   source=... intent=... confidence=...
        2. INDEXING     memory=N knowledge=N graph=N
        3. ROUTING      route=... confidence=... reason
        4. EXECUTION    mode=... status=...
        5. LEARNING     queued -> pending=N processed=N failed=N
  - A "verbose" toggle switch that, when on, also expands a full raw
    trace tree under the workflow panel (see section 5 -- reuse the
    same trace-tree component here as a collapsed-by-default child).
  - Sending a message should optimistically show the user's message
    immediately, then show a "thinking..." indicator until the reply
    arrives (mock this with a ~1-2s delay against sample data for
    now).

--------------------------------
5. TRACE INSPECTOR SCREEN
--------------------------------
A detailed, collapsible tree view of the FULL per-turn cognitive
trace (this already exists as backend data called `last_turn_trace`
-- see the schema below). Render it as nested, expandable/collapsible
sections, not a flat JSON dump:

  TURN
    query, response preview, total duration, pipeline_success
  PERCEPTION
    normalized_input, language, confidence, basic_intent, entities,
    metadata (source, uncertainty, goal, reason)
  COGNITIVE ROUTE
    route, confidence, fallback_allowed, evidence (key/value list)
  BRAIN DECISION
    mode, status, any skill/goal/error fields present
  ACTION RESPONSE
    mode, status, response text, action payload, error (if any)
  CONTRACT VALIDATION TRACE (if present)
    a chronological list of {schema, status: PASS/FAIL, error?,
    timestamp} entries -- render PASS in green, FAIL in red.
  LLM BUDGET (if present)
    calls used/max, tokens reserved/max, remaining of each.

Include a dropdown/search to pick which recent turn to inspect (the
Dashboard's Activity History rows should each be clickable and jump
here with that turn pre-selected).
